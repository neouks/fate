# Planner 和 Worker 上下文前缀优化复审

本次优化已部署到 `context-prefix-20261019.1`。固定角色、Skill 索引和工具 Schema 的顺序，将 Worker 意图约定、工作目录以及实时约束放到宿主请求尾部。Planner 保留原有有界态势与事实引用，先提供目标和待办，再提供本轮通知。没有改变事实发布、意图领取、授权或双图调度规则。

主要收益是跨意图复用缓存。完整工具 Schema 的 DeepSeek 对照中，Worker 后两次请求命中率从 5.3% 提升到 87.5%，Planner 从 75.7% 提升到 80.5%。实际输入 Token 只小幅下降，不能把缓存收益解释为同等比例的上下文缩短。

## 实现

- `apps/server/src/agent/roles.ts`：Planner 和 Worker 启用 `stable-prefix-v1`。移除重复宿主约定；Planner 不再在 system 固化约束，仍在每次请求尾部读取最新约束。Worker 保留用户自定义角色正文，将当前意图约定与资产索引交给宿主上下文装配。
- `apps/server/src/agent/prompt-context.ts`：目标、能力和待办先出现；变化、通知和触发说明后出现。近期事实按 ID 稳定排列，保留所有原有摘要和引用；frontier 优先级顺序不变。长数据继续通过原有有界 JSON 投影处理。
- `apps/server/src/pi/runner.ts`：使用 pi 原生 `before_agent_start` 和 `context` 扩展。system 中的 cwd 改为稳定的读取说明，实际目录在请求尾部给出；工具自身 cwd 不变。宿主上下文每次请求重建，不写入对话历史，因此不随轮数累积，也不会被会话压缩永久删去。
- `apps/server/src/pi/request-prefix.ts`：按工具名称、Schema 对象键稳定序列化。保留 Schema 数组、消息和工具调用顺序。遇到混合供应商专用工具时保持原样；不恢复禁用工具，不固定已经撤销的能力。
- `apps/server/src/tools/context-read.ts`、`apps/server/src/agent/tool-descriptions.ts`：区分正文与关系页续读；返回可直接复用的下一页参数，防止因为遗漏 offset 重读首页。
- `apps/server/src/agent/resources.ts`：稳定 Skill、MCP 服务及可见性配置的加载顺序，继续按权限过滤。
- `apps/server/src/agent/prompt-diagnostics.ts`、`apps/server/src/engine/runtime-config.ts`：记录策略版本、工具 Schema 哈希及宿主尾部大小。诊断不记录请求正文或凭据；字节估算不冒充供应商 Token。

角色默认正文和用户自定义提示词没有自动改写；数据库无需迁移。旧会话仍由 pi 读取，恢复时使用新装配和实时授权。配置、工具发现、权限或自定义提示词变化时，前缀允许变化，不能为了缓存使用过期配置。

## DeepSeek 成本对照

对照采用修改前实际代码与最终代码分别生成的 pi 原生 OpenAI 请求，经本地 HTTP 夹具抓取。每个角色、每个版本各三次不同动态上下文：Planner 是同任务连续变化，Worker 是同任务的三条不同意图。角色、工具绑定及合成资料一致；仅比较请求装配，按单次答复计费，不执行对照回复中的工具。

正式对照携带完整工具 Schema，`tool_choice=auto`。前后组使用独立缓存标识，交替请求，首次请求均为零命中。该实验是小样本、同一模型同一配置的测量，不代表生产任务的固定收益。

| 角色 | 版本 | 请求数 | 输入 Token | 输出 Token | 总 Token | 缓存读取 | 未缓存输入 | 全部请求命中率 | 后两次命中率 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Planner | 优化前 | 3 | 18,267 | 111 | 18,378 | 9,216 | 9,051 | 50.5% | 75.7% |
| Planner | 优化后 | 3 | 18,138 | 75 | 18,213 | 9,728 | 8,410 | 53.6% | 80.5% |
| Worker | 优化前 | 3 | 14,364 | 96 | 14,460 | 512 | 13,852 | 3.6% | 5.3% |
| Worker | 优化后 | 3 | 14,043 | 97 | 14,140 | 8,192 | 5,851 | 58.3% | 87.5% |

命中率使用供应商 `prompt_cache_hit_tokens / prompt_tokens`；此处 `prompt_tokens` 已包含缓存输入。Planner 输入下降约 0.7%，Worker 约 2.2%。合计总 Token 从 32,838 降至 32,353；输出文本不同带来的差异不归因于提示词优化。

本地平均请求体：Planner 22,431 → 22,320 字节，Worker 17,400 → 16,997 字节。相邻请求 messages 的公共前缀：Planner 2,556 → 4,096 字节，Worker 1,775 → 2,836 字节。供应商可能在 system 后插入工具定义，所以 JSON 字节公共前缀不能直接换算为缓存 Token。最终 Worker 的三个 system 哈希、工具 Schema 哈希分别一致。

[DeepSeek 官方缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)将缓存定义为完整前缀单元匹配，并明确是尽力提供、构建需要时间；本次保留了首次冷启动数据，没有将估算值算作实际命中。

## 按需读取与去重验证

新增六项回归覆盖：

1. 工具 Schema 顺序稳定，工具调用与数组顺序保持不变，禁用和混合工具不被重新加入。
2. Planner 原有摘要、版本和待办保留；动态事件后置，输入对象不被修改。
3. Worker 自定义角色和 Skill 索引正常；Skill 全文不预载；最新约束每轮刷新；恢复会话可读取已有事实且不重复写入。
4. Planner 通过搜索找到启动窗口之外的冷图事实、已完成意图，沿 `next_offset` 拼接完整中文及 emoji 证据；重复派单返回已有意图。
5. 原生压缩及重启后，当前意图约定、事实引用仍在，宿主尾部不会累积重复。
6. 正文续读返回可直接放入 `items` 的 `next_item`，自动沿用 ref、field、view、version 和 offset；关系页同时携带正确 cursor。逐页拼接得到完整证据，每页仍重新鉴权。原有 next_offset、page_cursor、next_cursor 契约保留。

真实模型在独立数据库执行了 Worker 和两个全新 Planner 会话。Worker 分页读完 4,418 字符合成证据，提取 `FATE_LOCAL_73`，只发布一条事实后结束；Planner 找到被较新记录挤出启动窗口的结果，完成目标证明。两轮前后意图总数均为 16，目标状态为 `met`。该验证调用真实领域工具；不是用模型输出文字代替数据库结果。

复审发现中间版本的工具说明混淆正文偏移与关系页游标，模型重复读了首页。已明确说明两种分页方式并新增 `next_item`。最终真实测试中 Worker 先读一次摘要，再按 0、3000 两个偏移读完节点正文，未重复第一页。既有自定义工具说明保留，只有准确匹配的旧内置文本升级。

先前测试中 Planner 两次无关 bash 尝试被守卫拒绝；最终版本没有出现 bash 尝试，但有一次格式错误的 context_search 参数被 pi 拒绝，后续有效查询完成。模型仍可能产生无效调用，本次不能声称额外尝试为零。

## 最终复审结论

本次改动未发现尚未关闭的 P1/P2。复审覆盖真实请求顺序、Schema 权限、实时约束、压缩恢复、事实续读、派单去重及用量口径。没有修改 pi 模型循环、双图、锚点或发布规则。

缓存提升主要适用于角色与工具集合一致的重复请求；MCP 新发现、权限撤销、模型切换和用户配置变化会正常改变前缀。纯自然语言、缺少结构化工作身份的语义重复不能只靠提示词给出绝对保证；本次覆盖已完成意图复用及既有结构化身份去重回归。

回退只需撤销本次 contextLayout、任务尾部装配和 Schema 排序改动，并重新构建、在执行器安全边界重启；无数据库回滚。保留本次之前的未提交改动及历史会话，不使用全仓 reset。
