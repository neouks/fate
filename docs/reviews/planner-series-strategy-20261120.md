# Planner 目标内主动规划与按需读取

参考 [Series Planner](https://github.com/neouks/series/blob/main/agent/planner.go) 的规划倾向，保留本平台的单问题验收、证据收敛和人工控制。

- 未完成目标仍有有效方向时主动推进；允许前置已满足的不同路线并行，2–3 条是选择倾向，不是配额。
- 已知信息充分时直接派单，只有身份、历史覆盖、进度或依据不明确时查询；取消默认提示、持续会话及兼容轮消息中的固定检索前置。
- summary 概括对象、问题和目的；一个独立验收问题一个意图，依赖实际结果的后续工作先保存计划。
- 证据充分就验收；确实缺少输入或授权时记录恢复条件，不凑单。未修改纠偏、暂停、停止、超时和去重执行逻辑。
- 规划策略在实际系统提示中只保留一份，设置页宿主协议和运行时配置摘要也包含它。Worker、Main、Reporter 不注入自主规划策略。
- 新迁移只精确升级上一版内置 Planner 提示词，追加历史；自定义文本及迁移后主动选择的旧版本保持不变。

## 验证

`pnpm typecheck` 通过。相关 Node 回归 25 项通过，2 项需要数据库的用例随后在独立 PostgreSQL 数据库中验证；独立数据库测试共 8 项通过（含迁移幂等、历史保留、自定义和主动回退）。

真实模型使用现有 Planner 配置的 `deepseek-flash`。生产数据库连接强制只读，仅读取模型配置；新建 `test_` 数据库执行真实领域工具，结束后删除；不启动调度器或 Worker。

复现命令（在 `apps/server` 执行，需本地数据库及模型网络）：

```sh
node --import tsx scripts/evaluate-intent-granularity.mts --run --strategy --out=/tmp/planner-strategy-new-run
```

| 场景 | 实际结果 |
| --- | --- |
| 信息完整、仅一项待解决问题 | 首个工具为 add_intent，派 1 项，无前置查询 |
| 两条前置已满足、不同机理的路线 | 同批派 2 项，分别核查构建替换和启动覆盖 |
| 依赖实际结果的后续问题 | 仅派 CSV 关联键识别；引用一致性核对保存为 pending 待办，明确排除在当前意图验收之外 |
| 现有证据充分 | 0 派单，prove_goal 返回目标 met |
| 输入缺失且无允许的获取方式 | 0 派单，说明缺少样本并保存恢复条件 |

核查了 15 次实际模型请求中的系统提示和工具声明，策略仅一份、工具名称不重复；上述最终五种场景均无工具错误。结果文件中的意图约定也人工核对，不能仅以派单数量替代语义验收。

首轮“信息充分”夹具缺文件路径，模型合理地先读详情；补齐路径和格式标准后通过直接派单断言。原依赖夹具混合了只读授权与登录动作，模型增加了授权判断，因此另用纯离线文件关联场景隔离验证依赖拆分，不将原夹具作为纯粹粒度验证的结论。

完整请求与结果仅保留在本机 `/tmp/fate-planner-strategy-20261120-v2`；纯离线依赖补验保留在 `/tmp/fate-planner-strategy-20261120-dependency`。这些是合成问题的规划测试，不代表长期生产效果或 Worker 实际完成率。

本次不部署，不迁移生产数据库，不改变现有任务状态。
